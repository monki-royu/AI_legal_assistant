AGENT 01 · 合同审核

📋 合同审核智能体

完整 16 节点串联流程：小红书意图前置过滤 → 意图路由 → 文档提取 → 合同分类 → 条款切分 → 数值抽取 → 合同审核AI → 合规审查 → 数值校验 → 5阶段检索链路 → 甲乙方识别 → 企查查资信查询 → 四路风险聚合 → 最终交付。每步节点均对应 LangGraph 图中注册的实际节点函数。

前置过滤 · START 入口
📱 N00

小红书意图识别 (xiaohongshu_publish_intent_node)

所有请求的第一站。LLM 判断用户是否想发小红书：是 → 走小红书发布链路（文案生成→图片生成→检查→发布→Markdown）；否 → 进入主意图路由。属于"前置过滤"架构模式。

START → 此节点 · 条件路由分流
意图路由 · 条件分流
🧭 N01

意图路由 (intent_router_node)

LLM 识别用户意图，输出 task_type 字段，分流至六大业务链路：
contract_review（合同审核，走完整 16 节点）/ compliance_review（合规审查，精简流程）/ legal_research（法律检索）/ legal_qa（法律问答RAG）/ other（LLM直接回答）。

条件边 · path_map 路由至各链路起点
↓ contract_review 路径 · 以下 N02-N16 为合同审核完整链路。compliance_review 路径同样从 N02 进入，但跳过合同分类逻辑（在节点内判断 task_type 简化处理）。
文档处理阶段 · N02-N04
📄 N02

文档提取 (doc_extract_node)

读取 uploaded_doc_path 指向的合同文件（PDF/Word/TXT），解析为纯文本写入 doc_text。支持 .docx / .txt / 纯文本直传三种模式。无文件时直接使用 input 字段作为合同文本。

🏷️ N03

合同分类 (contract_classify_node)

LLM 基于 doc_text 判定合同类型（买卖/租赁/借贷/服务/采购等），写入 contract_type。决定后续行业增强检索层与适用规则集。compliance_review 路径在此节点内简单跳过分类逻辑。

✂️ N04

条款切分 (clause_split_node)

将 doc_text 按条款结构切分为结构化条款列表 doc_clauses。支持按"第X条"编号切分和按段落切分两种模式，为后续条款级审核提供粒度控制。

三审串联 · N05-N07
🔢 N05

数值抽取 (numeric_extract_node)

从合同文本中抽取关键数值（单价/数量/总价/付款比例/违约金比例/质保期等），写入 extracted_numerics。为后续数值校验提供数据基础。

🤖 N06

合同审核AI (contract_ai_review_node)

基于 LLM 对 doc_clauses 逐条做风险审查，输出 contract_risk_items（合同风险项列表）。每条含风险描述、条款位置、建议修改等结构化字段。

第 1 路风险 · 合同条款风险
🛡️ N07

合规审查 (compliance_review_node)

对照法律法规（民法典/民事诉讼法/数据安全法等）检测合规性风险，输出 compliance_risk_items。合规红线刚性，不被商业条款审核结果降级。

第 2 路风险 · 合规风险 · 刚性不降级
✔️ N08

数值校验 (numeric_validate_node)

校验 extracted_numerics 的数值一致性与合理性（如：预付款+尾款+质保金=100%？违约金是否超法定上限？），输出 numeric_risk_items。基于 YAML 规则文件，Python 确定性执行。

第 3 路风险 · 数值校验 · 确定性规则 · 不依赖 LLM
法律检索 · N09a-N09e（5节点拆分子链路）
🔍 N09a

检索·意图分解 (retrieval_intent_decompose_node)

将用户输入/合同类型分解为多个检索子意图，决定后续检索策略。

📚 N09b

检索·基础层 (retrieval_base_layer_node)

FAISS 向量检索 + Neo4j 图谱检索，4路并行获取基础法律知识。

🔧 N09c

检索·增强查询 (retrieval_enhance_query_node)

基于基础层结果做增强查询，补充行业层与条款层检索。

🔀 N09d

检索·融合排序 (retrieval_fusion_sort_node)

RRF（Reciprocal Rank Fusion）融合多路检索结果，去重、排序。

📤 N09e

检索·输出 (retrieval_output_node)

整理检索结果为 research_context 与 citations（法规引用列表），供后续风险聚合与报告生成使用。

主体识别 + 资信查询 · N10-N11
👥 N10

甲乙方识别 (party_identify_node)

LLM 从合同文本中识别甲方/乙方名称，写入 party_a / party_b。同时识别用户立场 user_side（甲方/乙方/中立），影响后续风险聚合的立场化评分。

🏢 N11

企查查资信查询 (credit_check_node)

调用企查查 MCP API（Bearer Token + JSON-RPC 2.0 + SSE 流式），查询甲乙双方企业资信：工商基本信息、股东结构、失信记录、被执行人、经营异常、行政处罚。计算资信评分与风险等级（Low/Medium/High），输出 credit_risk_items 和 party_a_credit_info / party_b_credit_info。

第 4 路风险 · 企查查 MCP · 三级兜底（MCP-Bearer → AppKey-MD5 → Mock）
风险聚合 + 最终交付 · N12-N13
⚠️ N12

风险聚合 (risk_aggregate_node)

合并四路风险数据：① 合同条款风险 contract_risk_items + ② 合规风险 compliance_risk_items + ③ 数值风险 numeric_risk_items + ④ 资信风险 credit_risk_items。去重、定级、计算综合评分 overall_risk_score（0-100）与风险等级 risk_level（Low/Medium/High）。合规 critical/high 级风险不降级。

四路聚合 · 立场化评分 · 合规刚性不降级
📦 N13

最终交付 (final_delivery_node)

组装最终报告：生成 final_report_markdown（Markdown 格式详细报告）+ output（纯文本摘要）。含风险清单、法规引用、资信摘要、是否需律师复核 need_lawyer_review 等字段。每条风险带 source_tag（条款审核/合规审查/数值校验/资信查询），全程审计追溯。

END · 结构化输出 · 审计追溯
