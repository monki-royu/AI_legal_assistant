📦 JSON → TXT 转换 — 完全可以

当前 `data/knowledge_base/laws_docs.json`（2316条法规）可以一键转换回 TXT：

```bash
python -c "
import json
with open('data/knowledge_base/laws_docs.json', encoding='utf-8') as f:
    docs = json.load(f)
import os
os.makedirs('data/knowledge_base/txt', exist_ok=True)
for d in docs:
    txt = f\"# {d['law_name']}\\n# 章节: {d.get('chapter','')}\\n{d['article_no']} {d['content']}\\n\"
    with open(f\"data/knowledge_base/txt/{d['law_name']}.txt\", 'a', encoding='utf-8') as out:
        out.write(txt + '\\n')
print(f'转换 {len(docs)} 条完成')
"
```

你的 TXT 原始文件也仍在 `__001__clawler/法律法规/` 中。

## 🗄️ legal-documents 原来用的确实是 MySQL

| 组件 | legal-documents | 当前 | 差异 |
|------|----------------|------|------|
| 法规表 | MySQL (SQLAlchemy ORM) | JSON 文件 | 零依赖 vs 需服务 |
| 案例表 | MySQL | JSON 文件 | 同上 |
| 全文搜索 | Elasticsearch (ES) | BM25/FAISS | 服务 vs 纯 Python |

| 文档 ID | MySQL 自增 | md5 确定性 | 防重复 vs 需维护 |

## 🎯 技术选型推荐

**选 MySQL？** ❌ 不推荐 — 需要单独安装维护，关系型存法律条文没有语义关联能力。

**选 ES？** ❌ 不推荐 — 太重，你的数据量（2316条法规）本地 BM25 秒级搜索，完全不需要分布式检索引擎。

**选 Neo4j？** ✅ **推荐** — 理由：

| 你的需求 | Neo4j 满足度 |
|----------|-------------|
| "LLM 从 TXT 抽取实体与关系" | ✅ 实体=节点，关系=边，天然匹配 |
| "保存微调数据" | ✅ 实体-关系对可导出为微调 JSON |
| "LLM 生成 Cypher 语句" | ✅ 已有 `check_cypher_node` 校验 |
| "智能问答通过实体查询" | ✅ MATCH (e:Entity {name:'违约金'}) 精准定位 |
| "所有数据源平级，按需检索" | ✅ 每个数据源一个 Label |
| "其他智能体调用检索智能体" | ✅ 意图路由不变 |
| **单源纵向三级降级** | ✅ **可以应用到实体抽取阶段**：LLM→规则→默认分词 |

### 三级降级如何转移到知识图谱方案(对于法律入库抽取实体时降级抽取,实施检索策略也降级检索)
```
当前方案（全文检索）:
  FAISS → BM25 → 关键词扫描

你的方案（实体匹配→Neo4j）:
  LLM 实体抽取 → 规则实体抽取 → 降级为关键词全文检索
    ↑ 高精度       ↑ 中精度            ↑ 兜底(复用现有 search())
```


*总结建议：**
- ✅ Neo4j 才是正确方向（实体匹配精度远超全文检索）
- ✅ 现有 JSON/BM25 代码保留做降级兜底（保证永不空返回）
- ❌ 不要上 MySQL/ES（运维成本高，对项目规模太重）
