## 🧠 知识图谱 vs 当前检索策略 — 深度对比分析

### 当前架构（纯检索引擎 + JSON 知识库）

```
用户问题 → [意图识别]
            ├─ "查法条" → 法规查询（关键词+法律名过滤→BM25/FAISS→法条原文）
            ├─ "查案例" → 案例检索（关键词筛选→BM25→案例详情）
            ├─ "问答"   → 智能问答（LLM+检索增强→自然语言回答）
            └─ "其他"   → 各专用智能体
```

**数据存储**：`data/knowledge_base/*_docs.json` + `index/*.pkl`（纯文件，零依赖）

**优点**：零外部依赖，开箱即用，FAISS+BM25 检索速度极快（毫秒级）

**缺点**：无实体关联，无法回答"这个合同条款违反了哪条法律的哪个规定"这类需要路径推理的问题

### 🗺️ 数据迁移路径（JSON → Neo4j）

如果你要切换到知识图谱架构，数据存放方式需要改变：

```
当前: data/knowledge_base/laws_docs.json
     [{"law_name": "民法典", "article_no": "第584条", "content": "...", ...}, ...]

改为 Neo4j 导入流程:
1. TXT → LLM 实体抽取
   └─ 输入: 民法典第584条.txt
   └─ 输出: {
        "entities": [{"name": "违约金", "type": "法律概念"}],
        "relations": [{"from": "第584条", "to": "违约金", "type": "规定"}]
      }

2. LLM 生成 Cypher（需校验）
   └─ "CREATE (l:Law {name:'民法典'})-[r:CONTAINS]->(a:Article {no:'第584条', content:'...'})"

3. Cypher 校验（check_cypher_node 已有）
   └─ 语法检查 → 语义检查 → 执行写入

4. 智能问答时:
   └─ 用户提问 → 抽取实体("违约金") → 匹配 Neo4j 节点 → Cypher 查询 → 返回关联条款
```

### 📋 **第三、四层设计（与你原需求完全一致）**

**第 3 层 — RRF 多源融合 + 冲突消解**（可复用）
**关于"法规查询只需要查一条数据域，再走多源融合是否浪费内存"：**

你的判断是对的。当用户明确点进"📜 法规查询"页面时，意图已经锁定为 **只查法规**，此时不应走多源融合。设计应该是：

```
法规查询页面 → 意图锁定 → 仅挂载 laws 数据源 → 跳过 RRF 融合
案例检索页面 → 意图锁定 → 仅挂载 cases 数据源 → 跳过 RRF 融合
首页问答/智能体 → 意图未锁定 → 挂载全部数据源 → RRF 融合
```

这样：
- **专用页面**：单源直查，性能最优，无浪费
- **首页/智能体**：多源融合，召回最全

这个区分已经在 `retrieval_engine.py` 的 `mount_sources()` 中有实现基础，可以通过 `task_type` 参数控制挂载哪些数据源。
k = 60  # RRF 常数
score(d) = Σ 1 / (k + rank_s(d))  # 遍历所有数据源的排名结果
```
+ 4 套冲突消解规则（与数据源无关）：
  1. 上位法优于下位法 ← 从 Neo4j 节点 level 属性读取
  2. 新法优于旧法 ← 从 Neo4j 节点 date 属性读取  
  3. 特别法优于一般法 ← 从 Neo4j 节点 name 匹配
  4. 已废止降权 ← 从 Neo4j 节点 status 属性读取

**第 4 层 — 质量门禁 0.85 + 3 轮重试**（不变）
```
quality_score >= 0.85 → 返回结果，跳过北大法宝 MCP
quality_score < 0.85 → 第1轮重试（调整实体/关键词）
                    → 仍 < 0.85 → 第2轮重试
                    → 仍 < 0.85 → 第3轮重试
                    → 仍 < 0.85 → human_intervention_needed=True
                                  → 提示"是否调用北大法宝 MCP？"
                                  → 用户确认后才调用，控制 API 成本
```

**关键点**：这三层逻辑与数据源无关 — 无论底层是 JSON+BM25 还是 Neo4j+Cypher，第三、四层代码完全不需要修改。

### 🎯 结论

你的 Neo4j 知识图谱方案是**更好的长期方向**，实体匹配的精度远超全文检索。迁移时：

1. **保持现有代码不改**（`retrieval_engine.py` 做降级兜底）
2. **增量构建 Neo4j 层**（新建 `common/graph_store.py`，类比 `history_store.py` 的单一职责模式）
3. **第三、四层逻辑完全复用**（RRF 融合、冲突消解、质量门禁不受数据源更换影响）
