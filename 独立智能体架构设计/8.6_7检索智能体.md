# 法智引擎 -- 您的AI法律助理 

##  🔍 检索智能体（Legal Research Agent） 

**职责**：自然语言驱动的多轮法律检索

### 设计目标 

**输入标准化**：

上游智能体（如合同审核智能体、合规审查智能体）在调用检索智能体时，必须提供以下字段：

- 

  `contract_type`（合同类型，已分类）

- 

  `clauses`（条款列表，已切分）

- 

  `user_query`（用户问题，可选）

- 

  `custom_rules`（用户自定义规则，可选）

- 

  `required_sources`（可选，指定需要检索的源；若不指定则由检索智能体自动推断）

**检索智能体职责**：

- 

  从 `user_query` 和 `clauses` 中提取子查询（如果需要）

- 

  精准检索：从用户问题/合同条款中提取检索意图

- 

  根据 `contract_type` 和 `required_sources` 动态选择检索源

- 

  分层混合 —— 基础层全量并行，增强层按合同类型按需加载

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 1：基础层（所有合同必跑，全量并行）                   │
│ ──────────────────────────────────────────────────────────── │
│ · 法律法规检索 · 类案检索 · 私有知识库                     │
│ · 相对方资信                                               │
│   相对方 = 合同的"另一方"（你签合同，对方就是相对方）       │
│   资信 = 资产/资金状况 + 信用状况                          │
│   合起来：调查合同另一方的"家底"和"口碑"，判断他有没有能力、│
│   有没有信用来履行合同                                     │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│ Layer 2：行业增强层（按合同类型动态加载）                   │
│ ──────────────────────────────────────────────────────────── │
│ 根据合同类型标签，按需挂载对应检索路径                     │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│ Layer 3：条款级增强层（按具体条款特征触发）                 │
│ ──────────────────────────────────────────────────────────── │
│ 扫描到特定条款关键词时，动态追加检索                       │
└─────────────────────────────────────────────────────────────┘
```

**为什么不全用八大库混合检索？三个硬伤：**

**为什么不全按类型分叉？**

执行分层并行检索（基础层 + 行业层 + 条款层）

- 

  时效核验：自动识别法规是否现行有效、是否被修订/废止

- 

  权威排序：类案按"指导性案例 > 公报案例 > 典型案例 > 普通案例"排序

- 

  冲突消解：当检索结果相互矛盾时，给出权威性判断

- 

  可追溯输出：每条结论都附带法条原文 + 案例案号 + 出处链接

- 

  返回结构化检索报告

**不重复工作**：检索智能体不再包含 N1 文档解析 和 N2 合同分类 节点，这些节点属于上游。

### 具体每层查询规则 

#### Layer 1：基础层（4 路必跑，全合同通用） 

所有合同类型 → 无条件触发

- 

  L3 法律法规检索

- 

  L4 类案与裁判规则检索

- 

  L4.6 私有知识库检索

- 

  L4.7 相对方资信检索

**理由**：这 4 类是任何合同审查的刚需——

- 

  不管什么合同都要查法律有没有禁止性规定

- 

  不管什么合同都要看对方是不是失信被执行人

- 

  公司内部范本和历史意见永远是最贴近业务的参考

- 

  类案告诉你司法实践中这条条款怎么被判

#### Layer 2：行业增强层（按合同类型标签动态挂载） 

在 N3（合同类型分类器）输出 `contract_type` 后，用一个 **路由器节点** 按需挂载检索路径。

**不同合同检索路径举例**：

```
[N3 合同类型分类器]
 ↓
 contract_type = "construction" (建设工程施工合同)
 ↓
 [L2.5 行业检索路由器]
 ↓
 ┌─ 挂载 L4.5 行业标准检索（GB 50500 工程量清单等）
 ├─ 挂载 L4.8 市场基准检索（建材信息价、人工费指导价）
 └─ 跳过 L4.10 医疗合规库（与施工合同无关）
```

#### Layer 3：条款级增强层（扫描条款内容动态触发） 

这一层解决的是"一份合同横跨多个领域"的问题。比如一份 SaaS 合同里藏了一条"数据跨境传输"条款，光靠合同类型是 saas 不会去查数据合规，但扫描到关键词后应该触发。

**机制**：在 N4（条款切分）之后，对每条条款做轻量级关键词扫描，命中则追加检索。

**部分触发关键词**（可寻找行业专家，AI 生成）：

```
[N4 条款切分] → 逐条扫描
 ↓
 条款文本："甲方可将用户数据传输至境外服务器"
 ↓
 关键词命中：["数据跨境", "境外传输", "个人信息出境"]
 ↓
 动态追加挂载：
 ├── 监管规定检索（个人信息保护法、数据出境安全评估办法）
 └── 行业标准检索（GB/T 35273 个人信息安全规范）
```

### 可作为判断依据的知识源 

#### 🏛 第一类：法律法规与监管规定（已覆盖） 

- 

  检索源：国家法律法规数据库、国务院公报、部门规章、地方性法规、监管规定（如市场监管总局《合同行政监督管理办法》）、国际条约

- 

  典型依据：

  - 

    《民法典》合同编及合同编通则司法解释

  - 

    《合同行政监督管理办法》（总局77号令）——格式条款红线、禁止"最终解释权"等

  - 

    《招标投标法》《政府采购法》及实施条例

  - 

    行业监管规定（如《商业银行托管业务管理办法》《私募投资基金备案指引》）

- 

  在审查中的作用：判断合同条款是否违反法律强制性规定、是否违背公序良俗。

#### 📜 第二类：司法裁判规则与类案（已覆盖） 

- 

  检索源：最高人民法院指导性案例、公报案例、典型案例；各地高院裁判规则；司法解释配套典型案例

- 

  典型依据：

  - 

    最高人民法院《合同编通则司法解释》及配套典型案例（如"违约金超过实际损失30%部分不予支持"规则）

  - 

    山东高院《关于合同格式条款的24条裁判规则》

  - 

    最高院《建设工程施工合同案例裁判规则》

- 

  在审查中的作用：预测条款在诉讼/仲裁中可能被判无效、被调整的概率。

#### 🏢 第三类：企业私有知识库（已覆盖） 

- 

  检索源：内部合同范本、历史审核意见、公司规章制度、过往项目合同、法务批复记录。

- 

  在审查中的作用：确保审查结论符合公司内部风控标准和商业偏好。

#### 🆕 第四类：行业标准与技术规范 

- 

  检索源：国家标准全文公开系统（GB）、行业标准库（HG/T、JB/T、DL/T等）、企业标准公共服务平台、ISO国际标准。

- 

  典型依据：

  - 

    质量标准（如设备采购合同中的 GB/T 19001）

  - 

    工程建设标准（如施工合同的 GB 50500 工程量清单计价规范）

  - 

    金融行业规范（如 JR/T 金融科技行业标准）

  - 

    数据安全标准（如 GB/T 35273 个人信息安全规范）

- 

  在审查中的作用：

  - 

    审核"质量标准"条款是否明确（如"符合国家标准"应具体到哪一号标准）

  - 

    判断质保金比例、验收标准是否符合行业惯例

  - 

    技术参数条款的合规性与先进性

- 

  💡 例如施工合同审查时，质保金扣留比例、工程价款计算方式都需要对照行业规范

#### 🆕 第五类：相对方资信与履约能力数据 

- 

  检索源：

  - 

    国家企业信用信息公示系统

  - 

    中国裁判文书网（涉诉查询）

  - 

    中国执行信息公开网（失信被执行人）

  - 

    天眼查/企查查 API

  - 

    央行征信系统、税务信用等级

  - 

    行业协会黑名单

- 

  典型依据：

  - 

    对方是否被列入失信被执行人

  - 

    对方近 3 年涉诉情况与败诉记录

  - 

    注册资本、实缴资本、股东背景

  - 

    行政许可资质是否在有效期内

  - 

    市场监管行政处罚记录

- 

  在审查中的作用：

  - 

    决定是否需要增加担保、预付款保函、分期付款等风控条款

  - 

    判断对方是否具备履约能力

  - 

    国有企业还需穿透核查关联方关系

- 

  ⚠️ 凤城市政府合同管理制度明确要求："合同承办主体应当充分发挥天眼查、企查查、企信宝、国家企业信用信息公示系统等电子化手段，充分调查合同相对方的主体资格、资信状况、履约能力等情况"

#### 🆕 第六类：市场交易基准与商业惯例 

- 

  检索源：

  - 

    行业定价报告（如工程造价的《信息价》）

  - 

    大宗商品交易平台行情数据

  - 

    行业利润率基准数据库

  - 

    商业惯例文献（如 ICC 国际商会惯例、行业协会指引）

  - 

    同类合同条款市场调研数据

- 

  典型依据：

  - 

    违约金市场合理区间（司法实践：通常不超过 LPR 4 倍或实际损失 30%）

  - 

    质保金行业惯例（工程合同通常 5%-10%）

  - 

    预付款合理比例（建议 ≤30%）

  - 

    关联交易定价公允性（需对照近 6 个月可比交易）

- 

  在审查中的作用：

  - 

    判断合同条款是否显失公平

  - 

    评估定价是否公允（如关联交易是否偏离市场价 30% 以上）

  - 

    上海奉贤政府审核方案明确规定："参照司法实践，按市场价估算，超过市场价30%的认定为'过高'，低于市场价30%的认定为'过低'"

#### 🆕 第七类：内部授权与审批程序记录 

- 

  检索源：

  - 

    公司章程与授权文件

  - 

    董事会/股东会决议库

  - 

    内部审批流系统（OA）

  - 

    印鉴使用记录

  - 

    关联交易清单与豁免文件

- 

  典型依据：

  - 

    签约人是否有合法授权（授权委托书）

  - 

    该合同金额是否超过总经理/董事会审批权限

  - 

    是否涉及关联交易需特别披露

  - 

    是否需经国资监管部门事前备案（国企场景）

- 

  在审查中的作用：

  - 

    判断合同订立程序是否合规

  - 

    国企合同若未经公平竞争审查不得提交合法性审核

  - 

    上市公司关联交易需核查是否履行披露义务

#### 🆕 第八类：合同示范文本与格式条款库 

- 

  检索源：

  - 

    市场监管总局及省级市场监管部门发布的合同示范文本

  - 

    行业主管部门示范合同（如住建部《建设工程施工合同示范文本》GF-2017-0201）

  - 

    国际商会（ICC）合同范本

  - 

    公司历史合同模板库

- 

  典型依据：

  - 

    示范文本的必备条款清单

  - 

    格式条款的"显著提示"合规要求（《合同行政监督管理办法》第六条）

  - 

    格式条款无效情形清单（办法第七条、第八条）

- 

  在审查中的作用：

  - 

    对照示范文本查漏补缺（合同主要条款完备性审查）

  - 

    识别格式条款的合规风险（如"最终解释权归甲方"无效）

  - 

    商业银行托管合同审查需结合《证券投资基金托管业务管理办法》补充必备条款

### 不同合同类型的实际检索知识源对比 

**不同检索路径对应的不同检索方法**：

把所有检索方式抽象出来，本质是 4 种底层范式：

八大检索源 ≠ 八种检索方式，而是四类底层范式（精确匹配 / 向量 / 关键词 / 结构化查询）的不同组合。

- 

  有编号的（法条、标准）→ 精确匹配为主

- 

  自由文本的（类案、私有库、范本）→ 向量 + 关键词混合

- 

  实时数据的（资信、行情）→ API 结构化查询

- 

  监管文档 → 关键词 + 时效性过滤

通过策略模式 + 配置驱动，可以让每一类源自动选用最优检索方式，且新增源时只需注册一个新策略——这就是可复用检索架构的核心。

### 分层动态检索 + 并行调度 + 质量控制的 Legal Research Agent 

```
上游智能体（合同审核/合规审查）传入：
 - contract_type: "construction"
 - clauses: [{"id": "c1", "text": "..."}, ...]
 - user_query: "违约金50%是否过高？"
 - required_sources: ["statute", "case", "market"] (可选)
 ↓
[N1] 查询意图分解（仅当 user_query 不为空时）
 · 从 user_query 中提取法律要素，生成 sub_queries
 · 若上游已提供 sub_queries，则直接使用
 ↓
[N2] 检索源选择器
 · 根据 contract_type 和 required_sources（若提供）确定需要激活的检索源
 · 若无 required_sources，则从 contract_type 推断默认源
 ↓
[N3] 并行检索调度器（同时启动基础层 + 行业增强层）
 │
 ├─ [基础层] 强制并行（4路）
 │   ├── L3_statute 法律法规检索（精确+向量+关键词）
 │   ├── L4_case 类案与裁判规则检索（向量+图谱+关键词）
 │   ├── L7_private_kb 私有知识库检索（混合+权限过滤）
 │   └── L8_credit 相对方资信检索（结构化API）
 │
 └─ [行业增强层] 按 contract_type 动态挂载（0~N路）
     ├── 建设工程 → L5_industry_std + L9_market
     ├── 医疗健康 → L10_health_compliance + L5_industry_std
     ├── 金融/借贷 → L4_regulatory + L9_market
     ├── 采购/销售 → L9_market + L10_model_contract
     └── 通用/NDA → 跳过（不挂载额外源）
 ↓
[N4] 条款级增强层（扫描合同条款，动态触发加深检索）
 · 对每条条款进行关键词匹配：
   - 出现“价格”“金额”“费率”→ 触发 L9_market（加深检索）
   - 出现“保密”“知识产权”→ 触发 L6_national_std
   - 出现“违约金”“赔偿”→ 触发 L4_case（加深检索）
   - 出现“管辖”“仲裁”→ 触发 L4_case + L3_statute
 · 若触发的源已在基础层或行业层中，则跳过（避免重复）
 ↓
[N5] 多源结果融合器
 · 收集所有检索节点的结果
 · 去重（按 ID 或内容哈希）
 · 分数归一化（每个源内缩放到 [0,1]）
 · 权威性加权（法规 1.0 > 监管 0.9 > 类案 0.8 > 标准 0.7 > 私有 0.6 > 资信 0.5 > 市场 0.4 > 范本 0.3）
 · 时效性过滤（剔除已废止法规、过期案例）
 · 按加权分数降序排列，取 Top-K
 ↓
[N6] 冲突检测与消解（确定性代码）
 · 检测类型：
   - 法规之间冲突（新法 vs 旧法）
   - 案例之间冲突（不同法院相反判决）
   - 法规 vs 案例（法条字面含义与司法实践不符）
   - 私有知识库 vs 外部法规（内部规定与法律相悖）
 · 消解规则：
   - 法律效力优先：法律 > 行政法规 > 部门规章 > 司法解释
   - 案例层级优先：指导性案例 > 公报案例 > 典型案例 > 普通案例
   - 时间优先：新法优于旧法
 · 输出：消解后的结果列表 + 冲突说明（用于报告）
 ↓
[N7] 引用格式化
 · 将每条结果转换为标准法律引用格式（含案号、法条编号、链接）
 ↓
[N8] 质量评估网关
 · 评估维度：
   - 覆盖率：是否覆盖了所有 required_sources（基础层必达）
   - 相关性：Top-3 结果的平均语义相似度 ≥ 0.75
   - 时效性：所有引用法规均为现行有效
   - 冲突消解率：检测到的冲突是否全部消解
 · 条件路由：
   - 质量分 ≥ 0.85 → [N9] 结构化输出
   - 质量分 < 0.85 且 retry_count < 3 → 返回 [N3] 重试（带反馈，调整检索参数）
   - retry_count ≥ 3 → 人工中断（LangGraph interrupt）
 ↓
[N9] 结构化输出
 · 输出格式：
   {
     "summary": "关于XX问题的法律研究结论",
     "key_findings": [...],
     "applicable_statutes": [...],
     "governing_cases": [...],
     "market_benchmarks": [...],
     "conflicts": [...],
     "recommendation": "建议修改条款为...",
     "citations": [...],
     "quality_score": 0.89,
     "retrieval_path": ["基础层:statute", "行业层:market", "条款层:case"]
   }
```

#### [N1] 查询意图分解器 

- 

  **输入**：用户原始问题 + 合同上下文（合同类型、条款内容、用户角色）

- 

  **处理逻辑**：

  - 

    识别查询的法律领域（合同法、劳动法、数据合规等）

  - 

    提取关键实体（条款类型、金额、主体等）

  - 

    分解为多个子查询（如："违约金过高如何调整" → ["民法典585条", "违约金调整 30%", "最高院指导案例"]）

  -

#### [N3] 并行检索调度器 

**LangGraph 实现**：

#### 可复用检索策略类设计 

```
class RetrievalStrategy(ABC):
    @abstractmethod
    def retrieve(self, query, **kwargs) -> List[Result]:
        pass

# 四大基础策略
class ExactMatchRetrieval(RetrievalStrategy):  # 精确匹配
    """用于：法律法规编号、标准编号、文号"""

class VectorRetrieval(RetrievalStrategy):      # 语义向量
    """用于：类案、私有知识库、范本"""

class KeywordRetrieval(RetrievalStrategy):     # BM25
    """用于：监管规定、行业标准"""

class StructuredQueryRetrieval(RetrievalStrategy):  # API/SQL
    """用于：相对方资信、市场基准"""

# 复合策略
class HybridRetrieval(RetrievalStrategy):      # 混合
    def __init__(self, strategies: List[RetrievalStrategy], weights: List[float]):
        self.strategies = strategies
        self.weights = weights

    def retrieve(self, query, **kwargs):
        all_results = []
        for strategy, weight in zip(self.strategies, self.weights):
            results = strategy.retrieve(query, **kwargs)
            for r in results:
                r.score *= weight
            all_results.extend(results)
        return rrf_fusion(all_results)
```

**按合同类型动态选择检索方式**：

```
retrieval_strategy_by_source:
  # 法律法规：精确 + 向量 + 关键词 三路并行
  statute:
    strategies: [exact_match, vector, keyword]
    weights: [0.5, 0.3, 0.2]

  # 监管规定：关键词 + 向量，强调时效性

    strategies: [keyword, vector]

    post_filter: validity_check

  industry_standard:
    strategies: [exact_match, keyword]
    weights: [0.7, 0.3]

  # 私有知识库：混合
  private_kb:

    weights: [0.5, 0.5]

  # 相对方资信：纯 API（不走 RAG）

```

#### 法律法规检索节点 

**特点**：法条有明确编号（《民法典》第585条），且同一法条可能有不同表述版本。

**检索方式组合**：

- 

  精确条文检索：用正则匹配"第X条"、"民法典"等编号 → 直接定位

- 

  向量语义检索：把用户问题 embedding 后检索最相似的法条

- 

  关键词 BM25：匹配法律术语（"违约金"、"不可抗力"）

**为什么这么组合**：

- 

  编号精确匹配保证"说到第585条就真的找到585条"；

- 

  向量检索解决"用户描述不清但语义相近"的问题。

```
if re.match(r"第\d+条", query):
    results = exact_article_search(query)  # 精确优先
results += vector_search(query, top_k=10)  # 语义兜底
results += bm25_search(query, top_k=5)    # 关键词补充
```

#### 监管规定检索 

**特点**：大量 PDF/HTML 文档，时效性强，常有"已被XX号文废止"的情况。

**检索方式组合**：

- 

  关键词检索：匹配发文机关、文号（"银保监发〔2023〕1号"）

- 

  向量语义检索：匹配监管意图

- 

  时效性过滤：按 `effective_date` 和 `status` 字段过滤

**为什么这么组合**：监管文档编号体系复杂，单纯向量检索容易召回过时版本，必须加时效性过滤。

```
results = vector_search(query) + keyword_search(query)
results = filter_by_validity(results)  # 剔除已废止
results = sort_by_recency(results)     # 新的优先
```

#### 裁判规则 / 类案检索 

**特点**：案例之间有引用关系、相似关系，案由和争议焦点是核心维度。

**检索方式组合**：

- 

  向量语义检索：匹配事实相似度

- 

  案例图谱检索：沿"引用-被引用"、"同案由"边扩展

- 

  结构化过滤：按法院层级、案由、年份过滤

**为什么用图谱**：最高院指导性案例被后续案例反复引用，图谱能捕捉"效力传导"关系。

```
MATCH (c:Case)-[:SAME_CAUSE]->(target:Case)
WHERE c.embedding <-> $query_embedding < 0.3
RETURN target
ORDER BY target.authority_level DESC
```

#### 行业标准 / 技术规范检索 

**特点**：标准有唯一编号（GB/T 19001-2016），且分为"强制性"和"推荐性"。

**检索方式组合**：

- 

  标准编号精确检索：正则匹配 `GB\s?\/?\s?T?\s?\d+`

- 

  关键词检索：匹配标准名称

- 

  向量语义检索：匹配技术内容

```
if re.match(r"GB[\/\s]?T?[\s]?\d+", query):
    results = standard_no_search(query)  # 精确优先
else:
    results = vector_search(query) + keyword_search(query)
```

#### 企业私有知识库检索 

**特点**：文档类型杂（Word/PDF/Excel/批注），有权限要求，需结合业务上下文。

**检索方式组合**：

- 

  混合检索（向量 + 关键词加权融合，RRF 算法）

- 

  元数据过滤：按部门、合同类型、保密级别

- 

  权限过滤：基于用户角色剔除无权限文档

**为什么用混合**：私有库既有"按模板写的规范文档"（适合关键词），也有"自由表述的审核意见"（适合向量），必须两者结合。

```
vec_results = vector_search(query, filters={"dept": user.dept})
kw_results = keyword_search(query, filters={"level": user.clearance})
fused = rrf_fusion(vec_results, kw_results, k=60)
```

### [N4] 条款级增强层 

- 

  **输入**：合同条款列表 + 已完成的检索结果（避免重复）

- 

  **处理**：

  - 

    对每条条款运行关键词规则引擎（确定性代码，非 LLM），若命中则触发对应的加深检索节点

  - 

    加深检索：例如对“违约金”条款，再次调用 L4_case 但使用更窄的查询（如“违约金 50% 过高 判例”），并设置更高的 top_k

  - 

    防重复：若加深的源已经在本次检索中出现过，则跳过（通过 state 中的 `completed_nodes` 集合判断）

### [N5] 多源结果融合器 

- 

  **输入**：所有检索节点输出的 `results` 列表

- 

  **算法**：Reciprocal Rank Fusion (RRF) + 权威性加权

- 

  **步骤**：

  1. 

     收集所有检索节点的 `results` 列表

  2. 

     去重：相同 ID 或高度相似的内容只保留一份

  3. 

     分数归一化：每个源内部的分数缩放到 [0,1]

  4. 

     时效性过滤：剔除已废止法规、过期案例

  5. 

     对每个结果赋予 `source_weight`（来自权威性映射表）

     - 

       `statute`: 1.0

     - 

       `regulatory`: 0.9

     - 

       `case`: 0.8

     - 

       `standard`: 0.7

     - 

       `private_kb`: 0.6

     - 

       `credit`: 0.5

     - 

       `market`: 0.4

     - 

       `model`: 0.3

  6. 

     对每个源内的排名计算 RRF 分数：`score += 1/(k + rank) * source_weight`

  7. 

     按总分降序排列，截取 Top-K

- 

  **输出**：`fused_results`（排序后的统一列表）

### [N6] 冲突检测与消解 

- 

  **检测类型**：

  - 

    法规之间冲突（新法 vs 旧法）

  - 

    案例之间冲突（不同法院相反判决）

  - 

    法规 vs 案例（法条字面含义与司法实践不符）

  - 

    私有知识库 vs 外部法规（内部规定与法律相悖）

- 

  **消解规则**（确定性代码实现，不依赖 LLM，使用规则引擎）：

  ```
  def resolve_conflicts(results):
      conflicts = []
      for i, a in enumerate(results):
          for j, b in enumerate(results[i+1:]):
              if are_conflicting(a, b):
                  resolution = resolve_pair(a, b)
                  conflicts.append(resolution)
                  # 根据消解结果调整分数
                  if resolution["winner"] == "a":
                      b.score *= 0.5  # 降权
                  else:
                      a.score *= 0.5
      return results, conflicts
  ```

- 

  **输出**：

  ```
  {
    "resolved_results": [...],
    "conflicts": [
      {
        "between": ["law_001", "case_005"],
        "description": "民法典第585条规定...但最高院指导案例认为...",
        "resolution": "以法规为准，案例作为参考",
        "recommendation": "建议采用法规规定，同时注意司法实践倾向"
      }
    ]
  }
  ```

### [N8] 质量评估网关 

- 

  **评估维度**：

  - 

    覆盖率：是否覆盖了所有 `required_sources`

    `coverage = len(actual_sources) / len(required_sources)`

  - 

    相关性：Top-3 结果的平均语义相似度 ≥ 0.75

    `relevance = average(cosine_sim(top3_results, query))`

  - 

    时效性：所有引用法规均为现行有效

    `timeliness = 1 if all statutes valid else 0`

  - 

    冲突消解率：检测到的冲突是否全部消解

    `conflict_resolution_rate = resolved_conflicts / total_conflicts`

- 

  **条件路由**：

  ```
  quality_score = 0.3*coverage + 0.4*relevance + 0.2*timeliness + 0.1*conflict_resolution_rate
  quality_score >= 0.85 → [N8] 输出
  quality_score < 0.85 且 retry_count < 3 → 返回 N1 重试（带反馈）
  retry_count >= 3 → 人工介入（interrupt）
  ```

### 架构设计对比 

✅ **最终设计原则总结**

💡 **关键设计要点**：

- 

  **模块解耦**：检索智能体不依赖文档解析，可被多个上游智能体复用（合同审核、合规审查、条款咨询等）。

- 

  **避免重复计算**：上游已经完成了文档提取和分类，检索智能体无需重复。

- 

  **输入灵活**：上游可以精确指定需要检索的源，也可以让检索智能体自动推断。

- 

  **策略模式**：每个检索节点内部使用可配置的策略组合，新增检索源只需实现一个节点并注册。

- 

  **并行加速**：所有检索源同时运行，互不阻塞，整体延迟取决于最慢的源。

- 

  **确定性门禁**：冲突消解和质量评估使用确定性代码，避免 LLM 幻觉影响关键判断。

- 

  **可观测性**：每个节点记录检索耗时、结果数量、来源，方便调试和审计。

- 

  **弹性重试**：质量不达标时自动重试，重试次数耗尽后升级人工。

- 

  **可独立测试**：检索智能体可以单独测试，只需构造模拟输入。
